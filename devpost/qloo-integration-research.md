# Qloo integration research

Checked October 13, 2026 against first-party Qloo documentation and the working [Qloo Agentic Hackathon rules](https://qloo.devpost.com/rules). This note supports the approved Android MVP; it does not register the project, guarantee eligibility, or verify an API key.

## Documented integration facts

Hackathon-issued keys require `https://hackathon.api.qloo.com`, fail against staging/production, and require **GET** Insights calls. Numeric quotas are unpublished and adjustable per user; keys deactivate after judging. [Hackathon developer guide](https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide). Keep the host configurable for the provisioned environment. Authenticate through the `X-Api-Key` header. [Authentication](https://docs.qloo.com/reference/api-onboarding).

| Operation | Exact route and useful inputs | Documented response envelope |
| --- | --- | --- |
| Entity resolution | `GET /search`; `query=<name>`, `types=<comma-separated supported types>`, conservative `take=5` | `success`, `duration`, **`results[]`**. This is not the Insights envelope. |
| Broad-interest/tag lookup | `GET /v2/tags`; `filter.query=<interest>`, optional `filter.tag.types`, `take=10` | `success`, `duration`, **`results.tags[]`**. The published endpoint schema leaves tag item properties unspecified. |
| Cultural recommendations | `GET /v2/insights`; required `filter.type`, plus at least one valid signal/filter; use resolved `signal.interests.entities` and/or `signal.interests.tags`, optional `filter.tags`, `take=5`, `feature.explainability=true` | `success`, **`results.entities[]`** for entity recommendations. Treat timing metadata as optional: schema and examples place `duration` differently. |

The live endpoint pages embed their operation schemas in the public HTML's `script#ssr-props`. They confirm the envelopes above, header authentication, and comma-separated GET lists. [Entity Search](https://docs.qloo.com/reference/get-search), [Tags Search](https://docs.qloo.com/reference/get-tags), [Insights](https://docs.qloo.com/reference/insights-api-deep-dive), [required Insights input](https://docs.qloo.com/reference/basic-insights-use-case).

Entity examples contain `entity_id`, `name`, `type` (often the generic `urn:entity`), **`subtype`** (the actual category), optional `properties.description`, `properties.image.url`, `disambiguation`, `popularity`, `tags[]` containing `{id,name,type}`, `external`, and `query`. Normalize an entity to `{id: entity_id, name, category: subtype, description?, imageUrl?, disambiguation?, tags?, provenance}`. Do not interpret `type: urn:entity` as the category or assume that optional properties exist. [Basic Insights example](https://docs.qloo.com/reference/basic-insights-use-case).

Tag-based Insights examples use `tag_id`, `name`, `types[]`, `subtype`, `tag_value`, and `query`; embedded entity tags instead use `id/name/type`. These are different documented forms. Normalize them separately rather than assuming every Qloo tag has `id`. The `/v2/tags` item schema is open, so a provisioned-key test must establish its actual lookup-item fields before implementing its decoder. Do not silently guess between `id` and `tag_id` in a supposedly verified contract. [Tag Insights example](https://docs.qloo.com/reference/taste-analysis), [Tags Search schema](https://docs.qloo.com/reference/get-tags).

`feature.explainability=true` requests per-result `query.explainability` showing input-entity contributions, plus aggregate top-level `query.explainability`. Contributions are normalized 0–1; computation can fail with `query.explainability.warning` while recommendations still succeed. Its exact nested shape is not fully specified on the parameter page and needs a real-response check. Preserve it as optional provenance and never treat it as Japanese proficiency, factual authority, or a probability that the learner will learn successfully. [Explainability parameter](https://docs.qloo.com/reference/insights-api-deep-dive#featureexplainability).

## Recommended mapping for this product

Use a small allowlist: `urn:entity:place` for actual shrines/landmarks and food places, `urn:entity:book` for manga, and `urn:entity:tv_show` or `urn:entity:movie` for anime. Those category names appear in both the current endpoint schema and hackathon guide. Qloo has no documented special `shrine`, `manga`, or `anime` entity type. Search a named favorite, show disambiguation, and let the learner confirm it before saving the returned Qloo identifier. Specific-title and Japanese-place coverage remains untested. [Entity categories](https://docs.qloo.com/docs/entities-1), [hackathon supported types](https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide#supported-entity-types).

For broad chips such as **Shrines**, **Manga**, and **Anime**, preserve the app's chosen interest independently. Resolve relevant tags through `/v2/tags`, inspect their actual names/namespaces/types, then use returned IDs as `signal.interests.tags` or applicable `filter.tags`. Do not manufacture a URN from the English label or pass `"shrines"` as an entity ID. Use `filter.geocode.country_code=JP` only for supported place recommendations; country/geography filters are not universally applicable to books or anime. Keep vocabulary/grammar/difficulty under the reviewed curriculum and learner model. Qloo chooses cultural contexts, not teaching correctness or ability. [Lookup APIs](https://docs.qloo.com/reference/api-overview#supporting-apis), [type-specific parameters](https://docs.qloo.com/reference/available-parameters-by-entity-type).

The learner's chat topic overrides saved interests. Resolve a named favorite or broad-interest tag once, fetch a small relevant result set, then reuse it within the conversation. Explain suggestions with verified source inputs: “You chose anime; Qloo suggested this related series.” Where available, use entity-contribution metadata for a more specific reason. For tag-only results or an explainability warning, describe the matching interest/filter without claiming that Qloo returned a causal explanation. Save dislike/exclusion preferences, support changing context, and accept an unresolved interest with ordinary reviewed examples rather than invented Qloo results. This is a product recommendation, not a Qloo API guarantee.

## Minimal agent workflow and event interpretation

The rules require a working app integrating Qloo that functions as an agentic tool, uses an agent framework, or integrates Qloo into an existing agent. They also require a functional demo link and a public repository with an open-source license; an installable Android demo/test build can be supplied for judging. [Official project/submission requirements](https://qloo.devpost.com/rules).

**Recommended interpretation:** a bounded tutor agent can satisfy the project's intended agent design by choosing when to call real cultural-context tools from the current topic, inspecting returned data, and using it in level-appropriate conversation. Define tools such as `resolveFavorite`, `findInterestTags`, and `recommendCulturalContexts`. The model requests structured calls; server handlers validate allowed types, actual IDs, query size and returned fields, execute Qloo, and return a small factual context. The tutor then replies, asks a follow-up, or offers a related roleplay. Permit at most two tool rounds and a small call budget per turn, and retain trace/provenance for the demo. On topic changes, the agent can request new context; ordinary turns can reuse the existing result set. A backend that merely preloads recommendations into a fixed prompt should not be presented as demonstrated tool-calling agency. Eligibility is the organizer's determination; this design interpretation is not a guarantee.

Demo evidence should show a learner-chosen topic, an actual validated Qloo tool call, the returned entity/tag IDs in private trace output, and a resulting conversation suggestion. No simulated results should be labeled as live integration. Keep tool-call protocol behind the shared AI adapter, so both chosen model providers must pass the same real tool-calling validation before the switching demonstration is claimed.

## Reliability, data handling, and remaining checks

Private server-side caching is permitted without a stated time limit; public-repository response data is prohibited. [Caching FAQ](https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide#can-i-cache-qloo-api-responses-in-my-app). Recommendation: keep raw results/provenance private, use synthetic test fixtures, and never commit real snapshots/keys. This server-cache permission does not establish rights to redistribute raw responses into offline/mobile content; validate provisioned terms. Offline lessons can retain app-owned teaching and learner practice.

Recommended handling: private caching, bounded requests, timeouts, backoff for transient failures/429 with `Retry-After` when supplied, no repeated retry for authorization/configuration errors, and a visible generic-context fallback. Qloo failure must not interrupt downloaded lessons/reviews. The guide warns of silently ignored unsupported parameters and missing hackathon coverage causing empty results. [Troubleshooting](https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide).

Before build integration acceptance, test with the actual account: host/key validity, numeric quota/rate budget, `/search` item fields, `/v2/tags` item fields, supported shrine/manga/anime tags and favorites, nonempty Insights results, explainability shape/availability, errors, terms for learner-facing/offline storage, and both providers' tool-call traces. The guide's `destination`/`video_game` enum differs from the current operation schema's `locality`/`videogame`; its `/get-tags-1` reference link also returned 404 while `/get-tags` worked. Restrict the MVP to the stable allowlist above and confirm environment capabilities rather than merging conflicting lists. [Guide](https://docs.qloo.com/reference/qloo-llm-hackathon-developer-guide), [current Insights reference](https://docs.qloo.com/reference/insights-api-deep-dive), [current tags reference](https://docs.qloo.com/reference/get-tags).

**Verification performed:** read public first-party pages, extracted embedded schemas, and inspected the official documentation source. **Not performed:** authenticated Qloo requests, live entity/tag resolution, quota/permission tests, agent/provider execution, registration, or submission. The public repository's `openapi-schema.json` is the generic OpenAPI document meta-schema, not Qloo's full endpoint specification; do not generate the adapter from that file. [Official documentation source](https://github.com/qloo/docs-public), [meta-schema file](https://github.com/qloo/docs-public/blob/main/openapi-schema.json).
